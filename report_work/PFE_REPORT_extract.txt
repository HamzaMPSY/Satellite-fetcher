[0033] (Heading 1) Abstract
[0036] (Normal) This report presents the design and implementation of an end-to-end satellite imagery acquisition and processing pipeline developed during an internship within Oracle's Digital Government context. The project addresses a practical need shared by public-sector geospatial use cases: analysts need a reliable way to define an area of interest, preview available scenes, launch provider downloads, normalize outputs into analysis-ready structures, and monitor the full execution lifecycle from a single operational interface.
[0037] (Normal) To answer this need, I contributed to a service-oriented platform composed of a FastAPI backend, background workers, a Streamlit user interface, an internal Zarr conversion runtime, and a mask service for cloud and water processing. The pipeline supports provider preview, asynchronous job orchestration, provider-aware download coordination, conversion of raw scenes to normalized scene-level Zarr stores, optional time-cube building, and execution both locally and on Oracle Cloud Infrastructure. The resulting platform improves traceability, reduces manual intervention, and provides a solid base for operational Earth-observation workflows.
[0038] (Normal) Keywords: Remote Sensing, Geospatial Pipelines, Satellite Imagery, Zarr, Microservices, Oracle Cloud Infrastructure

[0292] (Normal) Foundations and State-of-the-Art
[0296] (Normal) Introduction
[0298] (Normal) This chapter presents the technical foundations behind the satellite-processing platform developed during the internship. The project does not target a single isolated algorithm; instead, it addresses the engineering problem of turning heterogeneous satellite products into an operational, traceable and reusable pipeline. The following sections summarize the data foundations, execution concepts and architectural alternatives that guided the final design.
[0300] (Normal) Theoretical Background
[0302] (Normal) Building an operational Earth-observation pipeline requires more than geospatial knowledge alone. It also requires understanding how satellite products are packaged, how long-running tasks are orchestrated, how multidimensional raster outputs are represented and how runtime state is exposed to users and operators. These concerns define the engineering backbone of the project.
[0303] (Normal) Remote Sensing and Satellite Products
[0305] (Normal) The platform works with institutional satellite data providers such as Copernicus and USGS. These ecosystems expose products with different acquisition strategies, file formats, metadata conventions and access constraints. A practical pipeline therefore needs to abstract provider differences while preserving the scientific meaning of the downloaded scenes.
[0308] (Normal) Figure 9: Earth observation and remote sensing workflow
[0311] (Normal) Service-Oriented Geospatial Pipelines
[0313] (Normal) Operational Earth-observation systems are more reliable when they separate the control plane from the execution plane. The control plane receives user intent, validates parameters and records state, while the execution plane performs the heavy tasks such as downloads, conversions and post-processing.
[0314] (Normal) In this project, the public API centralizes preview, job creation, credential checks, artifact registration and runtime status retrieval.
[0315] (Normal) Background workers execute long-running actions such as scene download, Zarr conversion, time-cube generation and masking without blocking the user interface.
[0316] (Normal (Web)) This service-oriented design improves reproducibility, observability and deployment flexibility compared with isolated scripts.
[0318] (Normal) Cloud-Native Data Representation with Zarr
[0320] (Normal) Zarr is well suited to multidimensional satellite data because it stores chunked arrays, metadata and derived layers in a structure that can be accessed locally or through object storage. In this project, it is used as the normalized output format for scene-level products and for time cubes built from several scenes.
[0324] (Normal) Asynchronous Execution Foundations
[0325] (Normal) API Runtime and Public Endpoints:
[0327] (Normal) The FastAPI backend exposes endpoints for provider preview, job submission, provider status, worker status, mask health, artifact registration and result discovery.
[0328] (Normal) This runtime acts as the control plane: it validates requests, stores pipeline state and coordinates specialized execution services.
[0331] (Normal) Figure 10: Multi-service architecture of the platform
[0334] (Normal) Worker Runtime and Background Jobs:
[0335] (Normal) The worker processes queued jobs asynchronously and keeps a heartbeat so that the platform can distinguish alive, stale and unavailable execution nodes.
[0337] (Normal) Long-running tasks are detached from the HTTP request/response lifecycle and continue under a single persistent job identifier.
[0338] (Normal) Each pipeline run progresses through search, download, conversion, optional cube construction, optional mask generation and final readiness.
[0342] (Normal) Download Coordinator and Provider Limits:
[0343] (Normal) A dedicated coordinator manages active tasks while enforcing control-plane limits and data-plane limits that differ by provider.
[0347] (Normal) The coordinator also keeps per-account state for Copernicus downloads, making account-pool strategies possible when several credentials are configured.
[0348] (Normal) Retries, cooldown windows and task requeueing help the system recover from transient provider or network issues without losing the whole pipeline run.
[0351] (Normal) Artifact Lineage and State Persistence:
[0353] (Normal) Jobs, runtime events, outputs and coordinator tasks are persisted in SQLite so that the platform can restart cleanly and maintain traceability.
[0356] (Normal) Optional Accelerators and Deployment Modes:
[0358] (Normal) The platform supports several execution modes, from a fully local setup to GPU-backed runtimes and a hybrid Oracle Cloud Infrastructure deployment.
[0361] (Normal) Local and Hybrid Modes:
[0362] (Normal) Local mode is useful for development and debugging, while hybrid modes can externalize selected services such as masking when the host platform requires a specific accelerator path.
[0364] (Normal) OCI Full Mode:
[0365] (Normal) In OCI full mode, the API, worker, Zarr runtime and mask runtime execute on a remote GPU VM, while the Streamlit UI remains on the developer laptop and communicates through SSH tunnels and a bastion session.
[0367] (Normal) Operational Optimization:
[0369] (Normal) Provider-specific scheduling, health endpoints, runtime roles and script-based stack control make the platform easier to operate than a one-shot experimentation workflow.
[0370] (Normal) Storage Flexibility:
[0371] (Normal) Raw bundles and normalized outputs can target the local filesystem or OCI object storage, which keeps the processing chain close to the data when needed.
[0372] (Normal) Mask Services:
[0374] (Normal) Cloud and water masks are handled as explicit runtime stages that enrich existing Zarr stores instead of being hard-coded into the download step.
[0375] (Normal) This makes masking reusable and lets the pipeline stop at Zarr-only, cube-before-mask or cube-after-mask depending on the selected scenario.
[0376] (Normal) Observability:
[0378] (Normal) The user interface surfaces provider health, active stage, bytes downloaded, pipeline timeline, generated artifacts and runtime status so that problems are visible before they become silent failures.
[0379] (Normal) These capabilities are essential in operational contexts where long downloads and large raster products are common.
[0380] (Normal) Runtime Separation:
[0383] (Normal) Optional Post-processing Stages
[0385] (Normal) Once raw scenes are available, the platform can normalize them into scene-level Zarr stores while preserving imagery bands, ancillary layers and provenance metadata.

[0395] (Normal) State of the Art and Related Systems
[0397] (Normal) Many Earth-observation teams still rely on fragmented toolchains composed of shell scripts, notebooks and provider-specific utilities. Current practice is progressively moving toward cloud-native, service-oriented pipelines that are easier to monitor and scale.
[0400] (Normal) Monolithic download scripts:
[0402] (Normal) Simple shell-driven flows are fast to start with, but they make retry management, progress visibility and output lineage difficult as soon as multiple scenes or providers are involved.
[0404] (Normal) Notebook-based processing:
[0406] (Normal) Notebooks remain valuable for exploration, yet they are not ideal as an operational backbone for long-running downloads, artifact registration and repeatable deployment.
[0407] (Normal) Synchronous web applications
[0409] (Normal) A synchronous web application can preview data effectively, but it becomes fragile when the same process must also handle heavy downloads and conversions.
[0411] (Normal) Cloud-native EO pipelines
[0413] (Normal) Modern geospatial systems increasingly combine APIs, asynchronous workers, chunked storage formats such as Zarr and object-storage backends to bridge user interaction and production execution.
[0415] (Normal) Why the chosen architecture
[0417] (Normal) The architecture adopted in this project follows this trend while remaining intentionally lightweight: it separates public API, worker logic, conversion and masking services, but keeps the overall stack simple enough for iterative development inside the internship context.
[0418] (Normal) This balance between modularity and pragmatism is what makes the resulting platform suitable for Digital Government experimentation.
