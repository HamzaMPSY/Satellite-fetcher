# Zarr Data Model (v1)

This document freezes the standard Zarr model for the project.

It is the implementation baseline for task 3:

- target Zarr layout
- dimensions
- chunking
- compression
- required metadata

The canonical code source for this model is:

- `/Users/mehdidinari/Desktop/backend nimbus/src/nimbuschain_zarr_service/schema.py`

## Purpose

The Zarr model exists to ensure that:

- Sentinel-2 and Landsat can be normalized into the same internal structure
- `mask-service` can read a stable layout without provider-specific logic
- the orchestrator can reason about one standard artifact shape

## Versioning

Current format version:

- `zarr_format_version = 1`

Any breaking structural change must increment the format version explicitly.

## Target Layout

```text
<scene>.zarr/
  imagery/
  metadata/
  masks/
    cloud/
    water/
```

Rules:

- `imagery/` is the primary raster payload
- `metadata/` holds scene-level metadata and schema metadata
- `masks/cloud` stores the cloud mask generated by `OmniCloudMask`
- `masks/water` stores the water mask generated by `OmniWaterMask`

## Logical Dimensions

The canonical dimension order is:

- `time`
- `band`
- `y`
- `x`

Rules:

- single-scene jobs must write `time=1`
- multi-scene stacks are out of scope for v1

## Canonical Bands

The first canonical band set is:

- `blue`
- `green`
- `red`
- `nir`
- `swir1`
- `swir2`

Provider-specific sources must be mapped into these names before writing.

## Minimum Bands Required By Masking

For `OmniCloudMask`:

- `red`
- `green`
- `nir`

For `OmniWaterMask`:

- `red`
- `green`
- `blue`
- `nir`

If these bands are missing, masking must fail explicitly.

## Default Chunking

Default chunk shape for v1:

- `time=1`
- `band=1`
- `y=1024`
- `x=1024`

Reasoning:

- `time=1` matches single-scene jobs
- `band=1` keeps band access predictable for downstream masking
- `1024x1024` is a practical starting point for tiled raster I/O

This can be tuned later, but the current value is the agreed baseline.

## Default Compression

Default compression for v1:

- codec: `blosc`
- cname: `zstd`
- compression level: `5`
- shuffle: `bitshuffle`

Reasoning:

- strong default compression
- widely used in Zarr workflows
- practical balance between size and speed

## Required Metadata Fields

Every written Zarr store must preserve at least:

- `provider`
- `collection`
- `scene_id`
- `acquisition_datetime`
- `crs`
- `transform`
- `band_names`
- `zarr_format_version`

These fields are the minimum contract required by:

- downstream masking
- orchestration
- future debugging / reproducibility

## Runtime Exposure

The `zarr-converter-service` exposes this schema at:

- `GET /schema`

This makes the current model machine-readable and helps downstream services stay aligned.

## Example Machine-Readable Shape

The service returns a JSON structure containing:

- layout paths
- dimensions
- canonical bands
- metadata fields
- default chunk shape
- default compression
- required mask bands

This endpoint is intentionally simple and versioned for future automation.
